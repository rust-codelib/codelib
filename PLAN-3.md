# Этап 3: один шаг SPA

**Статус:** этап 3 реализован и завершён. Ниже зафиксированы фактический публичный API, численные соглашения, проверки и оставшиеся ограничения.

Основание: этап 3 из [GENERAL-PLAN.md](GENERAL-PLAN.md), контракты [PLAN-1.md](PLAN-1.md), завершённый кодер из [PLAN-2.md](PLAN-2.md) и требования [Codelib.md](Codelib.md). Спецификация и список задач находятся в этом файле; отдельные `SPEC.md` и `tasks/todo.md` не создаются.

## 1. Результат и границы

Результат этапа — рабочий расчёт одной итерации SPA (Sum-Product Algorithm, алгоритм суммы и произведения) по разреженной проверочной матрице H. Реализация подготавливает канальные LLR, учитывает стирания, обновляет сообщения проверок, итоговые LLR битов и сообщения переменных для следующей итерации.

Публичный учебный помощник `spa_step` позволяет выполнить один шаг и проверить результат без готового декодера. Внутреннее состояние подготавливается для повторного использования на этапе 4. `spa_step` каждый раз начинает с канального входа: повторный вызов функции не продолжает предыдущую итерацию.

Цикл `SpaDecoder`, остановка по синдрому, применение бюджета итераций, контракт `Decoder`, конфигуратор, `DecodeResult`, счётчики и события относятся к этапу 4. Здесь не реализуются извлечение восстановленного сообщения, байтовая упаковка, модель канала, другие алгоритмы или полиномы. Один шаг выполняется даже при исходном нулевом синдроме; начальную проверку остановки позже делает декодер.

Текущие `Bit`, `ParityCheckMatrix`, `Encoder` и `SystematicEncoder` уже работают. Их контракты сохраняются. Граф SPA строится по исходной H, без RREF, перестановки столбцов или удаления зависимых строк. Ограничение кодера `0 < rank(H) < n` к одному шагу SPA не применяется: нулевая и полноранговая H тоже допустимы.

## 2. Публичный API

```rust
#[derive(Debug, Clone, Copy, PartialEq)]
pub struct DecoderConfig { /* закрытые поля */ }

impl DecoderConfig {
    pub fn try_new(
        max_iterations: usize,
        llr_limit: f64,
    ) -> Result<Self, LdpcError>;

    pub fn max_iterations(&self) -> usize;
    pub fn llr_limit(&self) -> f64;
}

// Default: max_iterations = 50, llr_limit = 20.0.
// Eq не реализуется: конфигурация содержит f64.

#[derive(Debug, Clone, Copy)]
pub struct DecodeInput<'a> {
    pub llrs: &'a [f64],
    pub erasures: &'a [usize],
}

#[derive(Debug, Clone, PartialEq)]
pub struct SpaStepResult { /* закрытые поля */ }

impl SpaStepResult {
    pub fn word(&self) -> &[Bit];
    pub fn posterior_llrs(&self) -> &[f64];
}

pub fn spa_step(
    checks: &ParityCheckMatrix,
    config: DecoderConfig,
    input: DecodeInput<'_>,
) -> Result<SpaStepResult, LdpcError>;
```

`DecoderConfig` и `DecodeInput` следуют контрактам первого этапа. `spa_step` и `SpaStepResult` — дополнительный рабочий API одного шага, а не реализация `Decoder`. Результат владеет двумя массивами длины n в исходном порядке столбцов H; сырые сообщения рёбер в публичный API не выходят. Синдром при необходимости вычисляется существующим `checks.syndrome(result.word())`.

Конфигурация неизменяема после создания. Допустим любой бюджет `max_iterations`, включая 0; память под число итераций не выделяется. Один шаг использует только `llr_limit`: даже при бюджете 0 функция выполняет ровно одну итерацию. Бюджет будет применяться циклом декодера на этапе 4.

`DecodeInput` заимствует массивы: ссылки действуют во время вызова, исходные значения не меняются и не сохраняются в результате. `Result` возвращает `Ok` с результатом либо `Err` с причиной отказа. Пример вызова:

```rust
use ldpc_codes::{spa_step, DecodeInput, DecoderConfig, LdpcError, ParityCheckMatrix};

fn main() -> Result<(), LdpcError> {
    let checks = ParityCheckMatrix::try_from_rows(
        3, vec![vec![0, 1], vec![1, 2]],
    )?;
    let result = spa_step(
        &checks,
        DecoderConfig::default(),
        DecodeInput { llrs: &[2.0, -1.0, 3.0], erasures: &[] },
    )?;
    assert_eq!(result.posterior_llrs(), &[1.0, 4.0, 2.0]);
    assert!(checks.is_codeword(result.word())?);
    Ok(())
}
```

## 3. Численные соглашения

### 3.1. Знак, диапазон и насыщение

LLR — логарифмическое отношение вероятностей: `L = ln(P(0) / P(1))`. Жёсткое решение: `L >= 0` даёт `Bit::Zero`, иначе `Bit::One`. Оба нуля, `+0.0` и `-0.0`, дают Zero; проверять знак через `is_sign_negative` нельзя.

Выбранный диапазон конфигурации: конечное `0 < llr_limit <= 20.0`. Значения по умолчанию — предел 20 и бюджет 50. Это политика первой реализации, а не математическое ограничение SPA: при пределе 20 аргумент `tanh(q/2)` по модулю не больше 10, что оставляет запас до единицы в `f64`. Повышение предела требует пересмотра численного метода и отдельных проверок.

Определить `clip(x) = x.clamp(-llr_limit, llr_limit)`. Ограничивать канальные LLR, сообщения q и r, а также выдаваемые posterior LLR. Конечные входы вне диапазона, включая `±f64::MAX`, насыщаются; они не являются ошибкой. NaN и обе бесконечности отклоняются до насыщения и применения стираний.

Не насыщать частичные суммы по мере обхода: это делает результат зависимым от порядка положительных и отрицательных слагаемых. Сначала вычислять полную ненасыщенную сумму, затем ограничивать отдельный итог.

При действующем пределе каждой оси H в 4096 у бита не больше 4096 соседних проверок. Полная сумма `L + sum(r)` по модулю не превосходит `4097 * 20 = 81940`; даже промежуточное вычитание одного r безопасно для `f64`. Не требуется складывать исходные значения порядка `f64::MAX`: они ограничиваются при подготовке.

### 3.2. Подготовка входа и стирания

Порядок проверок детерминирован:

1. Проверить `input.llrs.len() == checks.cols()`.
2. Проверить конечность всех LLR в порядке индексов, включая стираемые позиции.
3. Проверить все индексы стираний в порядке входа: каждый должен быть меньше n.
4. Проверить повторы позиций стираний в порядке входа; вернуть первый повтор.
5. Только после успешной проверки получить `channel[i] = clip(input.llrs[i])` и установить стираемые позиции в `0.0`.

Стирание означает «бит неизвестен», а не инверсию. Порядок списка стираний не влияет на численный результат. Пустой список допустим; можно стереть все позиции. Индексы всегда относятся к исходной H, включая изолированные столбцы.

Начальное жёсткое решение определяется по подготовленному `channel`. Оно понадобится для `changed_bits` на этапе 4; исходный вход до стираний не должен становиться диагностическим эталоном.

### 3.3. Устойчивое сообщение проверки

Для произведения t, исключающего ребро получателя, математическая формула:

```text
r = 2 atanh(t) = ln(1 + t) - ln(1 - t)
```

Вычислять через `ln_1p`: сначала `u = clamp(t, -(1 - f64::EPSILON), 1 - f64::EPSILON)`, затем `r = clip(u.ln_1p() - (-u).ln_1p())`. Это оставляет аргументы внутри области определения и избегает потери малых t при явном вычислении `1 + t`. Для `t == 0` возвращать `0.0`.

Используемые методы описаны в [официальной документации Rust для f64](https://doc.rust-lang.org/std/primitive.f64.html#method.ln_1p). Точность трансцендентных функций может различаться между платформами; тесты сравнивают их результаты с допуском. Использовать методы, доступные на MSRV 1.81, без зависимости от более новых `next_up`/`next_down`.

Нулевые множители обрабатываются без деления. При очень высокой степени произведение может округлиться до нуля — это допустимое ослабление сообщения, а не ошибка входа. Проверки устойчивости требуют конечности и соблюдения диапазона всех буферов; NaN не заменяется молча нулём.

## 4. Разреженное состояние

Внутренний модуль `spa.rs` содержит граф рёбер и состояние одного блока. Номер ребра — закрытый индекс `usize`; публичный новый тип не нужен.

Пронумеровать единицы H по строкам, внутри строки — по возрастающему номеру бита. Хранить списки `check_edges[j]` и `bit_edges[i]` с общими номерами рёбер, а также `edge_bits[e]`, указывающий бит ребра. Проверочная принадлежность определяется списком `check_edges`; отдельный дублирующий массив необязателен.

Инварианты: каждое ребро входит ровно в одну проверочную и одну битовую смежность; номера образуют `0..E`; `edge_bits[e] < n`; число рёбер совпадает с `checks.edge_count()`. Пустые и повторяющиеся строки сохраняются. Обратные списки строятся одним обходом, без поиска пары узлов на каждом обновлении.

Рабочие данные:

- `channel`, `posterior` — по n значений `f64`; жёсткое слово — n битов;
- `q` (бит → проверка) и `r` (проверка → бит) — по E значений;
- временные массивы преобразований `tanh`, префиксных и суффиксных произведений — по максимальной степени проверки, с местом для пустого произведения.

Проверять `checked_add`/`checked_mul` для числа элементов и байтов новых буферов, включая степень плюс один; при переполнении использовать `SizeOverflow`. Не выделять матрицу `m * n`. Память подготовки и состояния — `O(m + n + E)`; шаг — `O(m + n + E)` операций. Нехватка памяти отдельно не переводится в `LdpcError`, согласно текущему подходу проекта с обычным `Vec`.

Внутреннее состояние имеет рабочие операции создания, подготовки нового блока и одной итерации. Публичный `spa_step` использует именно их; будущий `SpaDecoder` переиспользует их без перестроения графа на каждой итерации. Состояние не хранит ссылки на входные массивы и не требует общего владения H с кодером на этом этапе.

Перед новым блоком сбрасывать все q/r, channel, posterior и слово. Инициализация: `r[e] = 0`, `q[e] = channel[edge_bits[e]]`, `posterior = channel`, слово определяется по channel. Ошибочный ввод не должен частично заменять предыдущее подготовленное состояние: сначала все проверки, затем запись рабочих данных.

## 5. Одна flooding-итерация

Flooding означает обновление целыми фазами. Для шага t использовать все старые q, затем все новые r, затем сформировать posterior и q следующего шага. Нельзя обновлять q во время обхода проверок: поздние проверки получили бы данные уже другой итерации.

### 5.1. Проверки → биты

Для проверки j со списком рёбер `e[0..d]` вычислить `v[a] = tanh(q[e[a]] / 2)`. Префиксные и суффиксные произведения начинаются с 1. Для ребра a исключённое произведение равно `prefix[a] * suffix[a + 1]`; по нему получить r из раздела 3.3.

Это линейный по степени обход без `total_product / v[a]`: деление ломается на нулевых LLR. Особые случаи:

- степень 0: нет исходящих сообщений; строка всегда даёт нулевой синдром;
- степень 1: пустое произведение равно 1; проверка требует бит 0, поэтому её единственное сообщение равно `+llr_limit`;
- степень 2: сообщение в одно ребро равно q другого ребра. Использовать эту точную формулу без обратного преобразования `tanh`/`ln_1p`.

Для степеней от 3 применять общий расчёт. Повторяющиеся строки — отдельные узлы и сообщения; не объединять их как «избыточные».

### 5.2. Posterior и жёсткое слово

По каждому биту i вычислить ненасыщенную сумму:

```text
total[i] = channel[i] + sum(r[e] по всем bit_edges[i])
posterior[i] = clip(total[i])
word[i] = Zero, если posterior[i] >= 0, иначе One
```

Изолированный бит сохраняет канальный LLR и своё начальное решение. Результат всегда имеет длину n, независимо от числа рёбер.

### 5.3. Биты → проверки

Для каждого ребра e бита i:

```text
q_next[e] = clip(total[i] - r[e])
```

Использовать **ненасыщенный** total. Выражение `clip(total) - r[e]` неверно: после насыщения теряется вклад остальных соседей. При степени бита 1 новое q равно channel; при степени 0 сообщений нет. q следующей итерации формируются только после завершения всей проверочной фазы.

Реализация обрабатывает крайние степени отдельными ветками: при степени бита 0 она напрямую копирует `channel` в posterior и принимает решение по нему; при степени 1 записывает `channel` в единственное `q_next`, не вычисляя `total - r`. Это сохраняет малые значения LLR и знак нуля, которые могли бы потеряться из-за сложения и вычитания. Для степени от 2 применяется формула выше с ненасыщенным `total`.

## 6. Ошибки

Существующие варианты `LdpcError`, `Display`, `Eq` и цепочка `LinearAlgebra::source` сохраняются. Добавить:

| Вариант | Поля | Условие |
| --- | --- | --- |
| `InvalidLlrLimit` | — | Предел не конечен либо вне `(0, 20]` |
| `LlrLengthMismatch` | `expected: usize, actual: usize` | Число LLR отличается от n |
| `NonFiniteLlr` | `index: usize` | NaN или бесконечность на входе |
| `ErasureIndexOutOfBounds` | `bit: usize, bits: usize` | Позиция стирания вне `0..n` |
| `DuplicateErasureIndex` | `bit: usize` | Позиция стирания повторяется |

Не хранить исходный `f64` в ошибке: NaN не поддерживает обычное равенство, а текущий `LdpcError` реализует `Eq`. Тексты `Display` объясняют диапазон или ошибочный индекс; тесты сравнивают варианты и поля. `WordLengthMismatch` остаётся ошибкой битового слова, а не массива LLR.

Бюджет 0, большие конечные LLR, нулевой LLR и отсутствие рёбер не являются ошибками. Неверные входы возвращают `Err` до вычислений, без паник, `todo!()` или успешного пустого результата.

## 7. Контрольные расчёты и тесты

Основные тесты — стандартные `#[test]`, без новых зависимостей. Внутренние q/r и граф проверяются модульными тестами; публичный API — интеграционными тестами.

### 7.1. Ручной пример со степенью 2

```text
H = [[1, 1, 0],
     [0, 1, 1]]
channel = [2, -1, 3], llr_limit = 20
рёбра: (check, bit) = [(0,0), (0,1), (1,1), (1,2)]

q_initial = [2, -1, -1, 3]
r         = [-1, 2, 3, -1]
posterior = [1, 4, 2]
q_next    = [2, 2, 1, 3]
word_initial = [0, 1, 0]
word_after   = [0, 0, 0], syndrome = [0, 0]
```

Пример проверяет исключение получателя и правильный порядок фаз. Для проверки повторного шага внутреннего состояния: `r_second = [2, 2, 3, 1]`, `posterior_second = [4, 4, 4]`. Это проверка ядра, а не цикл декодирования.

### 7.2. Нелинейный пример со степенью 3

Одна строка `[0, 1, 2]`, все три канальных LLR равны `ln(3)`. Тогда `tanh(ln(3)/2) = 1/2`, исключённое произведение — `1/4`, каждый r равен `ln(5/3)`, posterior каждого бита равен `ln(5)`. q_next остаются `ln(3)`, поскольку каждый бит имеет одну проверку.

Ожидаемые значения задавать этими независимыми выражениями; тест не должен повторять реализацию с префиксами. Дополнить смешанными знаками, одним и двумя нулевыми множителями. В частности, при одном нуле сообщение к его позиции может быть ненулевым, а к остальным позициям должно быть нулевым.

### 7.3. Пример общего плана

Для H и `LLR_1` из раздела 5 `GENERAL-PLAN.md` проверить слово после одного шага `[0, 0, 1, 0, 1, 1]` и нулевой синдром. Источник примера — [учебная статья об LDPC](https://habr.com/ru/articles/453086/). `LLR_2` использовать для независимого сравнения численных массивов одного шага; требование о восстановлении после нескольких итераций остаётся этапу 4.

### 7.4. Обязательные группы

| Группа | Проверки |
| --- | --- |
| Конфигурация | Default, бюджет 0, предел 20, положительный малый предел; отказ для 0, отрицательных, NaN, ±∞ и значения выше 20 |
| Ввод | Длины n−1 и n+1, пустой ввод; индекс первого нечислового LLR; NaN на стираемой позиции тоже отклоняется |
| Стирания | Пустой список, все позиции, несортированный список, повтор, индекс n и `usize::MAX`; исходный массив не меняется |
| Граф | Степени 0/1/2 со стороны проверок и битов, E=0, повторяющиеся строки, нулевая и полноранговая H; точные индексы рёбер |
| Нули и знаки | ±0 дают Zero; один/два нулевых множителя; нечётное/чётное число отрицательных множителей; очень малые LLR |
| Насыщение | ±`f64::MAX`, границы ±20; все буферы конечны и в диапазоне; ограничение применяется до `tanh` |
| Исключение r | При channel=15 и двух r=15: posterior=20, но каждое q_next=20, а не 5 |
| Порядок сумм | При channel=15 и r=[15, −15] posterior=15; не получать 5 из-за промежуточного clip |
| Высокая степень | Одна проверка с 4096 битами; один бит с 4096 проверками; конечность без плотного буфера |
| Повторное использование | Два шага ручного примера; подготовка другого блока полностью сбрасывает состояние; ошибка подготовки не меняет предыдущий блок |

Для нелинейных примеров использовать абсолютный и относительный допуски, например `1e-10 + 1e-10 * abs(expected)`. Конечность проверять отдельно: сравнение через допуск не должно пропускать NaN. Нули, биты, индексы, длины и ошибки сравниваются точно.

Дополнительный независимый эталон для маленьких графов: прямые обходы всех соседей кроме получателя, обычный `atanh` при умеренных LLR, явные степени 0/1/2 и та же политика насыщения. Сравнить q, r и posterior, включая второй шаг. Эталон не использует промышленный помощник сообщения проверки или тот же алгоритм префиксов. Проверки syndrome используют существующий API либо независимый XOR.

## 9. Проверки и критерий завершения

После небольших задач — `cargo test -p ldpc-codes`. Перед завершением реализации этапа:

```sh
cargo fmt --all -- --check
cargo clippy --workspace --all-targets -- -D warnings
cargo test --workspace
cargo test --workspace --release
RUSTDOCFLAGS="-D warnings" cargo doc --workspace --no-deps
cargo +1.81.0 check --workspace --lib
cargo run -p ldpc-codes --example spa_step
cargo test -p ldpc-codes --doc
```

Сохраняются edition 2021, MSRV 1.81, `std` и запрет `unsafe`. Новые зависимости не нужны. Embedded-проверка CI продолжает собирать только `gf2m`, `gfpm` и `rs-codes`. Изменения арифметики полей и `gf-linalg` для этого этапа не требуются.

Этап завершён, когда:

- [x] Конфигурация, знак LLR, диапазон и ошибки реализованы согласно контракту.
- [x] Стирания проверяются и превращаются в нулевой канальный LLR.
- [x] Один flooding-шаг правильно обновляет r, posterior и q_next по разреженным рёбрам.
- [x] Подтверждены ручные примеры, независимый эталон, степени 0/1/2, нули, насыщение и конечность.
- [x] Публичный помощник работает; состояние ядра допускает повторную итерацию и сброс для другого блока.
- [x] Проверки workspace, MSRV, документации и пример проходят; в коде этапа 3 нет активных заглушек или подавлений предупреждений ради будущего кода.
- [x] Документация и статусы соответствуют выполненному объёму; этап 4 не начат.

Нулевой синдром после шага подтверждает только допустимость слова, а не совпадение с переданным. SPA не гарантирует восстановление на любом графе; насыщение и округление могут влиять на сходимость. Скорость, бюджет памяти и точное число итераций второго примера здесь не нормируются.
