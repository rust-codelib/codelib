# Repairable Fountain Codes: спецификация v1

Дата профиля: 2026-10-15. Генератор, wire и контрольные значения v1 зафиксированы. Реализация находится в [fountain-codes](../fountain-codes/README.md); воспроизводимые проверки описаны в [руководстве по экспериментам](FOUNTAIN-EXPERIMENTS.md).

Документ определяет профиль реализации конструкции статьи. Генератор, байтовые представления и контрольные примеры являются контрактом совместимости v1. Структура приватных Rust-типов может меняться при сохранении публичного поведения. Источники: [статья](https://arxiv.org/abs/1401.0734v1), [опубликованный SplitMix64](https://prng.di.unimi.it/splitmix64.c). Новые зависимости Rust для этой спецификации не требуются.

Модель — стирания: транспорт обеспечивает целостность. Проверка уравнений обнаруживает часть повреждений. Ни block_id, ни seed не являются средством аутентификации.

## 1. Профили и сообщение

| profile_id (u16) | Тип | Полином (u32) | W, байт на элемент в payload |
|---|---|---|---|
| 1 | gf2m::Gf65536 | 0x0001002D | 2, little-endian u16 |
| 2 | gf2m::Gf256 | 0x0000011D | 1, u8 |

Номер протокола wire_version = 1. Алгоритм генерации привязан к паре (wire_version, profile_id). Неизвестная пара отклоняется. Переданный полином обязан точно совпасть с таблицей; произвольный модуль не допускается.

Обозначения: N — длина исходного сообщения в байтах; T — длина payload одной части; K — число исходных частей; L — число элементов поля в части; d — число случайных выборов.

- 0 <= N <= 4096; 1 <= T <= 4096; T % W = 0.
- K = N / T + usize::from(N % T != 0); L = T / W.
- N > 0 требует 1 <= d <= 65535 и d <= локального max_parity_draws.
- N = 0 требует K = 0 и d = 0. T остаётся допустимым положительным размером; L вычисляется, но решатель не создаётся. Декодер сразу Complete, message() = Some(&[]). Части пустого блока недопустимы.
- Порядок исходных частей соответствует порядку байтов. Последняя дополняется нулями до T байт. В GF(65536) нечётный последний байт — младший байт последнего u16.
- Восстановленная таблица X имеет K строк по L элементов. Сериализация идёт по строкам; отбрасываются только байты за исходной длиной N. Хвостовые нули внутри N сохраняются.
- Ненулевой padding исходной части является неверным входом. Если ненулевой padding обнаружен только при полном решении, поток становится Invalid.

block_id — непрозрачный [u8; 16], заданный вызывающим кодом; допустимы все значения. seed — u64, допустим ноль. Совпадение block_id не заменяет сравнения остальных полей descriptor. Для фиксированных K, seed, ID и профиля генератор не зависит от block_id, N или T; различный контекст всё равно запрещает смешивание пакетов.

SymbolId = u64. Значения 0 <= id < K задают систематические части; id >= K задают проверочные. u64::MAX — допустимый последний ID. Генерация по произвольному ID не ведёт скрытого счётчика; последовательный обход после u64::MAX возвращает окончание, без wrapping.

Helper logarithmic_draws(k: usize, c: f64) -> Result<u16, FountainError> проверяет k <= MAX_MATRIX_DIM и конечное c > 0. Для k = 0 возвращает 0, для k = 1 — 1; иначе ceil(c * ln(k)), с проверкой результата в 1..=65535 до преобразования. Это удобство настройки: возможные различия libm не влияют на передачу, поскольку descriptor хранит уже выбранное целое d. Локальный лимит d проверяется конфигурацией отдельно. Универсального значения c по умолчанию нет.

Первый пример: профиль 1, N = 4096, T = 64, K = 64, L = 32, d = 16. Эти параметры экспериментальные, не являются обещанием заданной вероятности восстановления.

## 2. PRNG и support проверки

Все значения и операции этого раздела — u64. Сложение и умножение выполняются по модулю 2^64, сдвиги логические. mix64 не увеличивает состояние:

```text
mix64(z):
    z = (z xor (z >> 30)) * 0xBF58476D1CE4E5B9
    z = (z xor (z >> 27)) * 0x94D049BB133111EB
    return z xor (z >> 31)

next(state):
    state = state + 0x9E3779B97F4A7C15
    return mix64(state)
```

Для каждого проверочного ID независимо инициализируются два локальных потока:

```text
DOMAIN_INDEX = 0x524643315F494458    // RFC1_IDX, числовая константа
DOMAIN_COEFF = 0x524643315F434F46    // RFC1_COF, числовая константа
index_state = mix64(seed xor mix64(id) xor DOMAIN_INDEX)
coeff_state = mix64(seed xor mix64(id) xor DOMAIN_COEFF)
```

Разделение потоков отделяет расход слов при выборе индексов от коэффициентов. Профиль — детерминированное инженерное приближение независимой случайности; различные начальные состояния не являются доказательством статистической независимости.

1. Вычислить threshold = (0_u64.wrapping_sub(K as u64)) % (K as u64), то есть 2^64 mod K.
2. Получать r = next(index_state). Если r < threshold, отбросить слово. Иначе принять индекс r % K. Выполнить ровно d принятых выборов с возвращением.
3. Объединить повторы и отсортировать различные индексы по возрастанию.
4. На каждый различный индекс потратить ровно одно next(coeff_state). Коэффициент — младшие 16 бит для профиля 1 или младшие 8 бит для профиля 2. Остальные биты отбрасываются; уплотнения нескольких коэффициентов в одном слове нет.
5. Нулевые коэффициенты удалить из рабочего support. Новых выборов вместо них не делать. Повторы индексов не суммируют коэффициенты.
6. Для каждой из L позиций вычислить сумму a_i * X[i] по ненулевому support. Пустой support даёт T нулевых байтов.

Для систематического ID support = [(id, one)], PRNG не вызывается. Для K = 0 этот раздел не вызывается. Для K = 1 явное d может быть больше 1: helper выбирает 1, но формат не запрещает другие положительные значения.

Состояние каждого SplitMix64 обходит все u64 без повторов, mix64 — перестановка u64. Следовательно, до d принятых слов будет не более threshold отклонённых: число вызовов индексного PRNG не превышает d + threshold <= d + K - 1. Отдельный произвольный предел повторных попыток, меняющий профиль, не вводится.

## 3. Бинарный формат

Все многобайтовые числа little-endian. Смещения и размеры ниже указаны в байтах. Никаких размеров usize, выравнивания Rust-структур или enum-discriminant из памяти в wire нет. Для одного значения parser требует точную длину; хвостовые байты отклоняются. Транспорт самостоятельно разделяет поток на пакеты.

### Descriptor: ровно 48 байт

| Смещение | Размер | Значение |
|---|---|---|
| 0 | 4 | ASCII RFCD |
| 4 | 2 | wire_version = 1 |
| 6 | 2 | profile_id |
| 8 | 16 | block_id, без перестановки байтов |
| 24 | 2 | N |
| 26 | 2 | T |
| 28 | 2 | K, сверяется с N и T |
| 30 | 2 | d |
| 32 | 8 | seed |
| 40 | 4 | полином из таблицы профилей |
| 44 | 4 | reserved = 0 |

Порядок проверок: точная длина, magic, версия, профиль, reserved, полином, N, T и кратность W, K, правило d для пустого/непустого сообщения. Затем принимающий компонент проверяет локальные ресурсы. Для ошибок с несколькими неверными полями возвращается первая по этому порядку.

### Пакет части: 64 + T байта

| Смещение | Размер | Значение |
|---|---|---|
| 0 | 4 | ASCII RFCS |
| 4 | 48 | полный descriptor в формате выше |
| 52 | 8 | SymbolId |
| 60 | 2 | payload_len = T |
| 62 | 2 | reserved = 0 |
| 64 | T | payload |

Для v1 выбран самодостаточный пакет с полным контекстом. Описание блока вызывающий код задаёт кодеку один раз; wire-пакеты повторяют его, чтобы исключить зависимость проверки контекста от состояния соединения. Это явные 64 байта накладных расходов на часть. Компактный формат со ссылкой на внешний контекст потребует отдельного формата/версии.

Parser сначала проверяет минимум 64 байта, RFCS, вложенный descriptor, reserved пакета, K > 0, payload_len = T, затем точное равенство длины 64 + T. Все проверки заявленных размеров предшествуют копированию payload. Максимальная длина пакета 4160 байт. После разбора push сравнивает все поля descriptor с настройками своего блока. Parser сам по себе не выбирает целевой блок декодера.

Размер standalone descriptor — 48 байт; трафик M пакетов — M * (64 + T), плюс 48, если описание отдельно передавалось один раз. Полиномы, заголовки и padding включаются в метрики wire-трафика. Контрольная сумма в формате v1 отсутствует согласно модели канала.

Фиксируются функции parse_descriptor(&[u8]) -> Result<BlockDescriptor, FountainError>, parse_symbol(&[u8]) -> Result<EncodedSymbol, FountainError>; симметричные методы to_wire() возвращают Result<Vec<u8>, FountainError>. Wire-parser допускает все представимые d; локальный max_parity_draws применяет компонент при приёме descriptor, а не глобальный parser.

## 4. Ресурсная политика

Значения ResourceLimits::default():

| Поле | Значение | Единица |
|---|---|---|
| max_parity_draws | 256 | принятых случайных выборов на проверку |
| max_unique_symbols | 16384 | успешно принятых уникальных ID декодера |
| max_catalog_entries | 16384 | зарегистрированных проверочных ID |
| max_catalog_edges | 1048576 | фактических ненулевых связей каталога |
| max_logical_buffer_bytes | 67108864 | расчётных байтов на компонент |

Поля закрыты проверяющим конструктором; значения положительны. max_parity_draws <= 65535, остальные ограничения задаются usize и проверяются на переполнение при применении. Настройки ресурсов локальны и в wire не входят. Увеличение лимитов явно задаёт вызывающий код. Ошибка содержит resource, actual и limit. SizeOverflow отличается от ResourceLimitExceeded.

Базис содержит не более K строк, каждая ось LinearSystem ограничена существующим MAX_MATRIX_DIM. Ограничение числа принятых ID не следует из оси матрицы. У Vector отдельный лимит длины не появляется. Предел 128 КиБ применяется к существующему преобразованию в массив коэффициентов, отдельно от ресурсной политики кодека.

### Точный расчёт учитываемого бюджета v1

Это воспроизводимый расчётный бюджет, а не измерение RSS. Обозначения: M — число принятых уникальных частей; C — число проверок каталога; E — число его ненулевых связей; s = min(d, K). Размер элемента обоих выбранных Rust-полей — 2 байта, включая Gf256. Индексы и служебные записи учитываются по фиксированным единицам, одинаковым на 32/64-битных платформах.

```text
R = 128 + 16*d + 16*s + 2*K + 4*L + 64 + T    // непустой блок
R = 0                                         // пустой блок

encoder_charge = 48 + 2*K*L + R
decoder_charge = 48 + 64*K + 2*K*L + N + R
                 + 2*K*(K + L) + M*(32 + T)
catalog_charge = 48 + 64*K + 64*C + 48*E + R
```

В расчёт включены descriptor, padded-источник кодера, строки коэффициентов/правых частей, точные копии payload в таблице дубликатов и их записи, индексы опорных строк, прямые/обратные связи каталога и рабочие данные. R резервирует генератор, кандидатную строку, преобразование payload и один формируемый пакет. В decoder_charge заранее зарезервированы полный базис 2*K*(K+L), решение 2*K*L и выходное сообщение N; реальные строки базиса могут выделяться постепенно. Поэтому рост ранга и завершение не требуют скрытого увеличения бюджета. В catalog_charge включены временные списки кандидатов для greedy-групп. Полная последовательность сырых PRNG-слов и все сформированные пакеты внутри кодека не накапливаются.

Накладные расходы аллокатора, неиспользованная capacity, фиксированный стек, код, статические таблицы поля, память observer/транспорта и результаты, уже переданные вызывающему коду во владение, в расчёт не входят. Реализация должна укладывать принадлежащие ей содержательные буферы в описанные категории; новые большие рабочие буферы требуют обновления расчёта и проверки приёмки. Это не квота процесса или суммарная квота всех созданных компонентов: encoder, decoder и catalog проверяют свои заряды отдельно.

Каждое сложение/произведение проверяется. Запрашиваемые реальные буферы дополнительно проверяются на len * size_of::<T>() и предел адресуемого среза isize::MAX. Перед вставкой вычисляется заряд с новым M; перед регистрацией — с новыми C и E. Полный базис уже учтён при создании декодера, поэтому после insert_equation не возникает нового отказа по расчётному бюджету. Зависимое уравнение не увеличивает ранг. Совпадающий дубликат не увеличивает M и остаётся допустимым при заполненной таблице. Повторная регистрация того же ID идемпотентна. Пустая проверка занимает одну запись и ноль связей каталога.

| Сценарий | decoder_charge | catalog_charge |
|---|---|---|
| N=4096, T=64, профиль 1, d=16, r=M=64, пустой каталог | 31792 | 5168 |
| N=4096, T=1, профиль 2, d=256, r=4096, M=16384, C=16384, E=1048576 | 34394357 | 51658997 |
| N=4096, T=2, профиль 1, d=256, r=2048, M=16384, пустой каталог | 9101558 | 143606 |
| N=4096, T=4096, профиль 2, d=256, r=1, M=16384, пустой каталог | 67678532 | 24898 |

Последний набор превышает бюджет декодера: лимиты действуют совместно, поэтому 16384 части не обещаются при любом T. Это допустимый отказ ResourceLimitExceeded до изменения состояния. Все строки проверяются скриптом контрольных примеров. Расчёт объёма не является замером производительности максимальных систем.

## 5. Окончательный контракт LinearSystem<F>

Новый тип добавляется в gf-linalg на этапе 1, над существующим FieldElement. Пример ниже фиксирует API; код с заглушками в библиотеку на этапе 0 не добавляется.

```rust
pub enum EquationInsertion {
    Independent { pivot_column: usize, rank: usize },
    Dependent,
    Inconsistent { rhs_column: usize },
}

impl<F: FieldElement> LinearSystem<F> {
    pub fn try_new(unknowns: usize, rhs_columns: usize) -> Result<Self, LinalgError>;
    pub fn unknowns(&self) -> usize;
    pub fn rhs_columns(&self) -> usize;
    pub fn rank(&self) -> usize;
    pub fn insert_equation(
        &mut self, coefficients: &[F], rhs: &[F],
    ) -> Result<EquationInsertion, LinalgError>;
    pub fn try_solution(&self) -> Result<Option<Matrix<F>>, LinalgError>;
}
```

EquationInsertion реализует Debug, Clone, Copy, PartialEq, Eq. Поля LinearSystem закрыты, тип по умолчанию F = Gf256, как у Matrix. unknowns и rhs_columns находятся в 1..=MAX_MATRIX_DIM; нулевая система обрабатывается внешним фонтанным слоем.

Добавить в LinalgError варианты InvalidLinearSystemDimensions { unknowns, rhs_columns }, EquationCoefficientCountMismatch { expected, actual }, EquationRhsCountMismatch { expected, actual }, SizeOverflow. Существующие варианты и их поведение сохраняются. Порядок проверки insert: число коэффициентов, число правых частей, затем работа с копией строки. Источники не меняются и не сохраняются по ссылке.

Базис — нормализованные ступенчатые строки с возрастающими индексами пивотов. Новая строка последовательно исключается по текущим пивотам; те же операции применяются ко всем RHS. Первый оставшийся ненулевой коэффициент определяет новый pivot_column; его нормализуют и строку вставляют по месту. Новые пивоты могут приходить не в возрастающем порядке. Старые строки не обязаны немедленно приводиться к RREF.

Нулевой остаток коэффициентов и RHS даёт Dependent; ненулевой остаток RHS при нулевых коэффициентах — Inconsistent с первым ненулевым столбцом RHS, начиная с нуля. Эти два исхода и ошибки формы не меняют базис. Противоречие не «отравляет» сам LinearSystem: решение прежних согласованных уравнений доступно, а Invalid — политика фонтанного декодера.

rank < K даёт Ok(None). rank == K даёт Ok(Some(X)) размера K × L через обратный ход с восстановлением исходного порядка неизвестных. Условие решения A*X = Y. Несколько RHS решаются одними коэффициентами. Отдельные A/B сохраняют предел каждой оси; обратная матрица и Matrix ширины K+L для решения не строятся. Функция try_solution не меняет базис.

## 6. Контракты кодера, декодера и события

Уточнение API от 2026-10-18: coding-core 0.1.0 реализован. Нормативные роли определены его исходниками и [README](../coding-core/README.md). Собственные методы ниже уточняются для подключения к общему договору; wire_version, генератор, представления полей и JSON-контрольные значения не меняются. LDPC/RS не мигрируют в рамках фонтанной реализации.

Подготовка использует FountainConfigurator с проверенной RepairableConfig. PrepareBlock<'a> содержит message: coding_core::Message<&'a [u8]> и block_id: [u8; 16]. FountainConfigurator реализует Encoder<PrepareBlock<'a>>, возвращая подготовленный RepairableEncoder. Конструктор RepairableEncoder::try_new может оставаться прямым способом подготовки с теми же проверками.

RepairableEncoder реализует SymbolEncoder<u64>. RepairableDecoder реализует IncrementalDecoder<&EncodedSymbol>. Для независимых блочных попыток предусмотрен RepairableBatchDecoder: Decoder<&[EncodedSymbol]>.

```text
RepairableEncoder::try_new(message: &[u8], block_id: [u8; 16], config: RepairableConfig)
    -> Result<Self, FountainError>
encoder.descriptor() -> &BlockDescriptor
SymbolEncoder::symbol(&encoder, id: u64, observer: &mut dyn Observer<EncodeEvent>)
    -> Result<EncodedSymbol, FountainError>

RepairableDecoder::try_new(descriptor: BlockDescriptor, limits: ResourceLimits)
    -> Result<Self, FountainError>
decoder.descriptor() -> &BlockDescriptor
decoder.rank() -> usize
IncrementalDecoder::progress(&decoder) -> DecodeProgress
IncrementalDecoder::result(&decoder)
    -> Option<&Candidate<Message<Vec<u8>>, RecoveryChecks>>
decoder.message() -> Option<&[u8]>
IncrementalDecoder::push(&mut decoder, symbol: &EncodedSymbol,
    observer: &mut dyn Observer<DecodeEvent>) -> Result<PushOutcome, FountainError>
```

Observer — coding_core::Observer; для вызовов без логирования передаётся NoopObserver. Отдельные DecodeObserver/RepairObserver не определяются. EncodeEvent сообщает Prepared { message_bytes, source_symbols } после успешной подготовки и SymbolGenerated { id, payload_bytes } после успешной генерации; все размеры usize, ID u64. Ошибки подготовки и генерации не отправляют эти события.

Проверка исходной длины использует MessageBytes::try_new из coding-core, а не собственную вторую константу. Output потокового декодера — Candidate<Message<Vec<u8>>, RecoveryChecks>; кандидат заимствуется через result(). Проверки описывают полный ранг, согласованность принятых уравнений и допустимый padding, без утверждения о равенстве оригиналу или криптографической целостности. В Invalid result() и message() возвращают None.

RepairableBatchDecoder создаётся для проверенного descriptor и limits. Каждый decode обрабатывает новый независимый набор и проверяет все его части, включая поступившие после полного ранга. Возвращает DecodeOutcome::Candidate либо NeedMore с текущим прогрессом; ошибки входа и противоречия возвращаются через Result::Err. StopReason = core::convert::Infallible: нормальная остановка без кандидата для этого точного Gaussian-решателя не нужна. Данные между блочными попытками не накапливаются.

EncodedSymbol, config и descriptor имеют закрытые поля, проверяющие конструкторы и читающие методы. Payload — T байт во владении, метод payload() -> &[u8]. Конструктор символа проверяет форму и непустой блок; семантику уравнения проверяет декодер. Decoder никогда не хранит ссылки на входной пакет. Конфигуратор создаёт согласованные компоненты с одинаковым descriptor; кодер сохраняет копию исходных данных.

DecodeProgress — NeedMoreSymbols, Complete или Invalid. PushOutcome содержит kind: SymbolOutcome, progress: DecodeProgress, rank: usize и unique_symbols: usize. SymbolOutcome — Independent, Dependent, Duplicate или Verified (новый согласованный ID после Complete). Число принятых ID и ранг доступны раздельно.

Порядок push: отклонить уже Invalid; проверить полный контекст и длину; найти ID в таблице дубликатов; проверить padding систематической части; проверить лимиты числа частей и рабочего бюджета с новым M; вставить уравнение и записать принятый ID при согласованном результате. Полный базис и завершение зарезервированы заранее, поэтому ресурсные ошибки не появляются после изменения базиса. Конфликт ранее принятого ID с другим payload возвращает ConflictingSymbol { id }, сохраняя прогресс и базис. Совпадающий дубликат возвращает Duplicate.

Новый противоречивый ID возвращает InconsistentEquation { id, rhs_column }, переводит поток в Invalid, сохраняя прежний базис и таблицу; этот ID не учитывается как принятый. После Complete новые части сверяются с полным восстановленным X, включая padding; Gaussian-вставка не нужна. При противоречии сохраняется rank = K, прогресс становится Invalid. В Invalid message() = None. Ранее выданные копии сообщения не отзываются.

При полном ранге ненулевой padding X приводит к NonzeroPadding { symbol_id, byte_offset } и Invalid. Независимая строка и принятый ID в этом случае уже добавлены, ранг остаётся K; это обнаруженное повреждение потока, а не обычная ошибка формы. Для неверного padding входной систематической части ошибка возвращается до вставки и прогресс сохраняется.

Наблюдение декодирования: coding_core::Observer<DecodeEvent>. Нормативные варианты и поля:

| Событие | Поля |
|---|---|
| Accepted | id: u64, unique_symbols: usize, rank: usize |
| RankIncreased | id: u64, previous_rank: usize, rank: usize, pivot_column: usize |
| Dependent | id: u64, rank: usize |
| Duplicate | id: u64, rank: usize |
| Verified | id: u64, rank: usize |
| Completed | rank: usize, unique_symbols: usize, message_bytes: usize |
| Invalidated | id: u64, rank: usize, reason: InvalidReason |

InvalidReason — Equation { rhs_column: usize } или Padding { symbol_id: u64, byte_offset: usize }. Для независимой части порядок Accepted → RankIncreased → при первом полном восстановлении Completed. Для новой зависимой — Accepted → Dependent; для дубликата — только Duplicate; после Complete новый согласованный ID даёт Accepted → Verified без второго Completed. Противоречивый новый ID даёт только Invalidated. Итоговый неверный padding даёт Accepted → RankIncreased → Invalidated. Обычные ошибки входа и ресурсов не дают событий принятия. Пустой блок создаётся Complete без push и без событий.

## 7. Локальный ремонт

RepairCatalog привязан к одному descriptor и локальным limits. register(parity_id: u64) -> Result<(), FountainError> принимает только ID >= K непустого блока, регистрирует canonical support, проверяя новые C/E до commit. Повторная регистрация идемпотентна. Поиск ведётся по конечному зарегистрированному каталогу.

```text
RepairCatalog: RepairPlanner<RepairRequest<'a>>
    Plan = LocalRepairPlan; Unavailable = RepairUnavailable
    plan(request, &mut dyn Observer<RepairEvent>)
        -> Result<coding_core::RepairPlan<LocalRepairPlan, RepairUnavailable>, FountainError>

StoredSymbol: RepairHelper<&HelperRequest>
    respond(request, &mut dyn Observer<RepairEvent>) -> Result<HelperResponse, FountainError>

RepairCatalog: RepairExecutor<ExecuteRepair<'a>>
    repair(input, &mut dyn Observer<RepairEvent>) -> Result<EncodedSymbol, FountainError>
```

RepairRequest содержит target и заимствованный available_ids. LocalRepairPlan — собственный проверенный план; coding_core::RepairPlan — общий enum Ready/Unavailable. Полный descriptor, target и helper_id связываются в HelperRequest и копируются в HelperResponse вместе с payload. StoredSymbol имеет доступ только к данным одного помощника и проверяет запрос до формирования ответа. Успешный ответ может отправить HelperResponded { target, helper_id, payload_bytes }; это событие вычисления ответа, а не измерение внешнего сетевого чтения.

ExecuteRepair содержит ссылку на LocalRepairPlan и callback read_helper:
FnMut(&HelperRequest) -> Result<HelperResponse, FountainError>. Исполнитель передаёт запрос из плана, проверяет descriptor, target, helper_id и форму ответа. Данные оригинала или потерянной цели не передаются.

Удобная функция repair_local(catalog, request, read_helper, observer) соединяет планирование и исполнение общих ролей. Прямые вспомогательные методы делегируют тем же операциям; параллельного собственного договора кодеков/ремонта нет.

Ни одна операция не запускает полный декодер. available_ids трактуется как множество, порядок и повторы не влияют; target игнорируется как помощник. Длинный входной список не копируется целиком: проверяется принадлежность по заимствованному срезу или строятся ограниченные флаги только для K исходных и C зарегистрированных проверочных частей. Для систематической цели перебираются зарегистрированные проверки с ненулевым целевым коэффициентом; для проверочной цели требуется её регистрация. Все помощники должны быть заявлены доступными. repair_local преобразует Ready в Some результата, а Unavailable в None, сохраняя смысл исхода общего планировщика.

Кандидаты сортируются по (число помощников, parity_id); выбирается первый. LocalRepairPlan закрыт от произвольного конструирования и содержит descriptor, target, выбранный parity_id и возрастающий список (helper_id, weight). Для исходной цели веса: a_target^(-1) у проверки, -a_target^(-1)*a_h у остальных исходных участников. Для проверочной цели — её исходные коэффициенты. У нулевой проверки список пуст, результат — нули. Отсутствие группы даёт Ok(coding_core::RepairPlan::Unavailable(...)), неверный вход — Err.

Execute проверяет контекст плана до чтений. Затем вызывает read_helper ровно один раз на HelperRequest, в порядке ID плана, проверяет целевой ID ответа, ID помощника, полный контекст и длину; данные цели и оригинала не передаются. Отсутствующий/неверный помощник прерывает операцию с ошибкой без готового результата. Метрики относятся к payload, успешно возвращённым read_helper, а не к физическому сетевому I/O, которое библиотека не наблюдает.

События ремонта передаются через coding_core::Observer<RepairEvent>. Варианты: GroupSelected { target, parity_id, helpers: usize }; HelperRead { target, requested_id: u64, returned_id: u64, payload_bytes: usize, read_symbols: usize, read_payload_bytes: usize }; Completed { target, read_symbols: usize, read_payload_bytes: usize }; Unavailable { target }. GroupSelected отправляет execute перед первым чтением; HelperRead — сразу после успешного возврата callback, включая payload, затем отклонённый по контексту/ID. Два ID позволяют честно отразить ошибочного помощника. Completed бывает только при успехе. Если callback возвращает Err, payload не получен и счётчики успешных чтений не растут. У нулевой проверки: GroupSelected → Completed, 0 чтений. Unavailable отправляет RepairPlanner::plan при отсутствии группы. GroupSelected отправляет только исполнитель; он не дублируется при планировании. При обычной ошибке запроса планировщик не отправляет событий успешной обработки.

Availability — greedy по тому же порядку кандидатов: взять группу, если её ID помощников не пересекаются с уже выбранными. Возвращается найденный набор, являющийся нижней оценкой числа непересекающихся групп; максимум не заявляется.

## 8. Контрольные примеры

Машиночитаемый контракт: [fixtures/fountain-v1.json](fixtures/fountain-v1.json). Все u64 ID записаны десятичными строками; seed/состояния/PRNG-слова — hex-строками без 0x, чтобы читатели JSON не теряли разряды. Массивы коэффициентов/RHS содержат целые представления элементов поля, не обычные целочисленные веса вне поля.

Для SplitMix64 с начальным состоянием 0 первые слова: e220a8397b1dcdaf, 6e789e6aa1b965f4, 06c45d188009454f. Для принудительного потока [0, 1, 2, u64::MAX] при K=3 threshold=1; 0 отклоняется, принятые индексы [1, 2, 0].

Общие параметры двух примеров: seed=0x0123456789ABCDEF, d=5, K=3, block_id=байты 00..0f. Для ID=3 индексы до объединения [2,2,2,1,1]; для ID=4 — [0,0,1,0,2]; для ID=5 — [1,2,0,2,2]. Эти индексы совпадают у обоих профилей; коэффициенты берутся из разного числа младших бит.

| Пример | Источник (hex) | T | Payload ID=3 | Payload ID=4 | Payload ID=5 |
|---|---|---|---|---|---|
| GF(256) | 80ff341200 | 2 | 0ede | 25ef | 5fd7 |
| GF(65536), нечётная длина | 8001ff0034120080aa55cc | 4 | 492a4761 | 4e65b693 | 68ba8092 |

В обоих примерах только ID=[3,4,5] дают ранг 3 и точный исходный результат. Последовательность новых пивотов при этих вставках [1,0,2] проверяет вставку пивотов не по порядку. Для GF(256) repair части 0 выбирает проверку 4; помощники и веса: (1,0x74), (2,0x8c), (4,0xb5), результат 80ff, 3 части/6 байт. Проверка: 0xf2 * 0xb5 = 1 в поле 0x11D. Для GF(65536) аналогичный ремонт читает 3 части/12 байт. Данные цели доступны только проверяющему коду как ожидаемый результат, а не процедуре ремонта.

Нулевая проверка: профиль 2, K=1, d=1, seed=0x224, id=1. Единственный индекс 0 получает коэффициент из слова 3fccd8c539033a00; младшие 8 бит нулевые, support пуст, payload 00. Повторной генерации нет.

Нечётная характеристика: над GF(5) решение X=[[2,0],[4,3]]. Вставки ([1,1],[1,3]) и ([2,1],[3,3]) дают ранг 1, затем 2. ([3,2],[4,1]) зависима. ([3,2],[4,2]) противоречива с rhs_column=1 и не меняет решение прежнего базиса.

JSON также фиксирует полный descriptor, пакет для каждого ID, id=u64::MAX, padding, сырые слова PRNG, RHS и результат полного декодирования, веса ремонта, пустой descriptor и расчёты ресурсного бюджета. Приёмочные Rust-тесты должны сравниваться с этими сохранёнными значениями, а не получать ожидаемые ответы вызовом тестируемого генератора.

Для проверки и явного обновления:

```sh
python3 tools/fountain_spec_vectors.py --check
node tools/check_fountain_spec.mjs
# Только после согласованного изменения спецификации:
python3 tools/fountain_spec_vectors.py --write
```

Python-скрипт — независимый арифметический эталон спецификации с batch Gauss-Jordan; он не заменяет потоковую Rust-реализацию или её тесты. JavaScript-проверка независимо вычисляет PRNG через BigInt и умножение через произведение/редукцию многочленов. Внешние библиотеки и сетевые загрузки для этих проверок не нужны.

## 9. Проверки совместимости

Rust-тесты в fountain-codes сравнивают поддержку, payload, wire, полное
восстановление, веса ремонта и расчёт ресурсов с сохранённым JSON. Тесты
gf-linalg отдельно проверяют решатель с несколькими правыми частями, неполный
ранг, противоречия, перестановки уравнений и поля нечётной характеристики.

```sh
cargo test -p gf-linalg -p fountain-codes
cargo +1.81.0 test -p fountain-codes
cargo fmt --all -- --check
cargo clippy --workspace --all-targets -- -D warnings
```

Полная конфигурация CI сохраняет workspace debug/release-тесты, rustdoc,
MSRV 1.81 и embedded-сборки существующих no_std-библиотек. Новый std-крейт
не включается в embedded-сборку. Статистические эксперименты имеют отдельные
конечные бюджеты и не заменяют проверки алгебраической корректности.
