# Общий план: крейт `ldpc-codes`

**Статус:** этапы 0–4 выполнены. Этапы 5–6 и дальнейшая работа остаются планом.

## 1. Цель и границы

Добавить в workspace библиотечный крейт для двоичных LDPC-кодов. Пользователь задаёт проверочную матрицу, кодирует сообщение, подаёт декодеру принятые мягкие значения, получает восстановленное слово и диагностику.

Основной источник требований — [Codelib.md](Codelib.md). Учебная статья [«Все, что вы хотели узнать об LDPC кодах, но стеснялись спросить»](https://habr.com/ru/articles/453086/) служит источником объяснений и контрольных примеров; при расхождении приоритет у ТЗ.

В первую версию входят:

- фиксированные интерфейсы кодера и декодера, конфигуратор и ошибки ввода;
- двоичный LDPC-код, заданный разреженной проверочной матрицей `H`;
- работа с битами и векторами коэффициентов с сохранением длины;
- систематическое кодирование и декодирование алгоритмом SPA;
- диагностика ошибок, журнал событий и поддержка позиций стираний;
- документация и примеры.

GUI, недвоичные коды, готовые профили DVB/Wi-Fi/5G, передача по моделируемому каналу, другие алгоритмы декодирования и оптимизация производительности не входят в первую версию. ТЗ не задаёт минимальной скорости или бюджета памяти; явные ограничения размеров перечислены в разделе 6.

Общий слой полиномов ещё не реализован. После его появления необходимо связать `gf-linalg` с ним преобразованиями вектора в полином и обратно и подключить эту связь к LDPC. Это обязательная отложенная часть ТЗ, описанная в этапе 6; собственный тип полинома внутри LDPC не создаём.

## 2. Где крейт находится в проекте

В workspace уже есть:

| Пакет | Назначение и связь с LDPC |
| --- | --- |
| `gfpm` | Поля `GF(p^m)`. Тип `gfpm::Gf<2, 1, 1>` представляет `GF(2)`. |
| `gf-linalg` | Плотные обобщённые матрицы и векторы. RREF и вычисление ранга уже доступны; LDPC использует их для подготовки кодера. |
| `gf2m` | Поля `GF(2^m)`, где минимальное поддерживаемое поле — `GF(4)`. Для первой версии двоичного LDPC не требуется. |
| `rs-codes` | Отдельный крейт Рида–Соломона с уже объявленными контрактами. Его интерфейсы не меняются в рамках LDPC. |

Новый пакет располагается в `ldpc-codes/`, имя библиотеки — `ldpc_codes`. Используются edition 2021 и MSRV 1.81 из workspace. Крейту нужны `std` и `Vec`, он зависит от `gfpm` и `gf-linalg`, не использует `unsafe` и не требует сторонних зависимостей.

### Что относится к какому крейту

В `gf-linalg` добавляются общие операции над плотной `Matrix<F>`: приведение к приведённому ступенчатому виду (RREF), номера опорных столбцов и ранг. Они должны работать для любого типа `F`, реализующего `FieldElement`, а не только для `GF(2)`.

RREF выполняет преобразования строк, оставляет столбцы в исходном порядке и возвращает матрицу той же формы вместе с упорядоченными индексами опорных столбцов. Нулевые строки находятся внизу. Ранг равен числу опорных столбцов. Исходная матрица не меняется.

В `ldpc-codes` остаются разреженная `H`, граф связей между проверками и битами, систематический кодер и SPA-декодер. Кодер преобразует `H` в `Matrix<Gf2>`, где `Gf2` — псевдоним для `gfpm::Gf<2, 1, 1>`, и использует RREF из `gf-linalg`. Декодер работает с разреженными связями и не создаёт плотную матрицу сообщений.

Полиномы будут отдельным общим слоем codelib. В `gf-linalg` уже есть преобразования вектора и строк матрицы в массивы коэффициентов и обратно, но это ещё не преобразования в настоящий тип полинома. Существующие модули `poly` в `gfpm` и `gf2m` также не заменяют будущий слой.

## 3. Данные и интерфейсы

### Путь сообщения

До появления полиномов:

```text
сообщение → Vector<Gf2> → кодер → кодовое слово
принятые LLR → декодер → информационный Vector<Gf2> → сообщение
```

Когда общий тип полинома будет готов, добавить преобразования `Vector<F> ↔ полином над F`. Требуемый ТЗ перевод сообщения в полином и обратно реализуется через этот адаптер для `Vector<Gf2>`. Имена типа, методов и место адаптеров выбираются по готовому API полиномов, без циклических зависимостей между крейтами.

Порядок уже задаётся существующим `gf-linalg`: элемент с индексом `i` соответствует коэффициенту при `x^i`. Например, `[1, 0, 1, 0]` задаёт `1 + x²`, но исходная длина равна 4. При будущем преобразовании в полином нужно сохранять эту длину: если полином удаляет хвостовые нули, обратному преобразованию потребуется явная длина вектора. Полностью нулевое сообщение также должно восстанавливаться без потери длины.

### Фиксированные контракты

Имена и сигнатуры описаны в [PLAN-1.md](PLAN-1.md) до реализации кодера и декодера. Разделение ответственности:

| Контракт | Вход | Результат |
| --- | --- | --- |
| `Encoder` | Ровно `k` информационных битов | Кодовое слово длины `n` в порядке столбцов исходной `H` либо ошибка входа |
| `Decoder` | Ровно `n` LLR; опционально позиции стёртых битов | Слово, статус остановки и диагностика либо ошибка входа |
| Конфигуратор | `H` и параметры декодирования; первая версия использует SPA | Согласованные кодер и декодер либо конкретная ошибка конфигурации |

В первой версии единственный алгоритм — SPA. Конфигуратор выводит `m`, `n`, ранг `r` и длину сообщения `k = n - r` из матрицы, чтобы нельзя было задать противоречивые размеры. Общие контракты Рида–Соломона здесь не меняются: у него другие входы и результаты.

### Проверочная матрица и систематический кодер

`ParityCheckMatrix` хранит `m × n` и только единицы `H`: связь каждой единицы доступна со стороны проверок и со стороны битов. При `E` единицах хранение связей занимает `O(m + n + E)`.

В GF(2) сложение — XOR. Синдром слова `c` — `s = Hc`; слово допустимо, если синдром нулевой. Нулевые или повторяющиеся строки допустимы для проверки синдрома и декодирования; при вычислении ранга зависимые строки учитываются.

Кодер использует `r = rank(H)`, а не число строк `m`. При `0 < r < n` свободные столбцы RREF выбираются информационными, опорные — проверочными. Кодер строит систематическую форму и хранит обе перестановки столбцов. На входе и выходе слова порядок всегда соответствует исходной `H`; извлекать сообщение простым срезом первых `k` битов нельзя, если столбцы пришлось переставить.

### SPA и числовые соглашения

LLR задаются как `Lᵢ = ln(P(0) / P(1))`: при `Lᵢ >= 0` решение равно 0, иначе — 1. Нулевой LLR означает отсутствие предпочтения и решается в пользу 0. Это соглашение соответствует формуле и коду примера в статье.

Используется flooding: сначала обновляются сообщения проверок, затем сообщения битов. Для ребра `i—j`:

```text
q(i → j) = Lᵢ + сумма r(j' → i) по j' != j
r(j → i) = 2 atanh(произведение tanh(q(i' → j) / 2) по i' != i)
posteriorᵢ = Lᵢ + сумма r(j → i)
```

Суммы и произведения обходят только соседние рёбра. До реализации в `PLAN-3.md` фиксируются численная граница LLR, защита от переполнения и устойчивый расчёт `atanh` для нулевых и больших значений. Нельзя получать исключённое произведение делением на сообщение: так нулевой LLR приведёт к `0/0`. Входные NaN и бесконечности отклоняются.

Декодер проверяет синдром исходного жёсткого решения до первой итерации. Если он нулевой, возвращается ноль итераций. Иначе выполняются итерации до нулевого синдрома или исчерпания бюджета. Исчерпание — нормальный статус результата, а не ошибка входа. Нулевой синдром означает, что найдено допустимое слово, но сам по себе не доказывает, что это переданное слово.

### Диагностика, логирование и стирания

Без эталонного сообщения декодер не может узнать настоящее количество ошибок. Результат декодера сообщает:

- `changed_bits` — сколько битов отличается от начального жёсткого решения;
- число невыполненных проверок до и после декодирования;
- число итераций и статус остановки.

Эти показатели не называются числом исправленных ошибок: декодер может изменить бит неверно. Точные ошибки считаются отдельным сравнением исходного и итогового слова с эталоном равной длины. Аналогично BER/FER в опыте вычисляются по известному исходному сообщению.

Логирование подключается через `DecodeObserver`, передаваемый для конкретного вызова декодера. События обозначают начало декодирования, конец итерации и остановку; содержат итерацию, диагностические показатели и статус. Без получателя лог не создаётся. Приёмочные проверки должны убедиться, что подключение логирования не меняет результат.

Для SPA предполагаемые позиции ошибок представлены как стирания: соответствующий LLR устанавливается в 0 до декодирования. Это значит «бит неизвестен», а не «бит нужно инвертировать». Индексы проверяются; повторяющиеся позиции отклоняются. Поддержка других видов подсказок зависит от конкретного алгоритма и требует отдельного контракта.

## 5. Контрольный пример и проверки

Из [примера статьи](https://habr.com/ru/articles/453086/) взять матрицу и два набора LLR:

```text
H = [[1, 1, 0, 1, 0, 0],
     [0, 1, 1, 0, 1, 0],
     [1, 0, 0, 0, 1, 1],
     [0, 0, 1, 1, 0, 1]]

expected = [0, 0, 1, 0, 1, 1]
LLR_1 = [-1.3863, 1.3863, -1.3863, 1.3863, -1.3863, -1.3863]
LLR_2 = [-0.5, 2.5, -4.0, 5.0, -3.5, 2.5]
```

Первый пример сходится за одну итерацию. Для второго проверить восстановленное слово и синдром; точное число итераций зафиксировать после утверждения численной политики. Статья — один контрольный источник, дополнительно нужны независимый syndrome, ручная проверка SPA и полный перебор маленького кода.

После этапа 0 запускать `cargo test -p gf-linalg`. После появления крейта запускать `cargo test -p ldpc-codes`; перед завершением этапа — проверки CI:

```sh
cargo fmt --all -- --check
cargo clippy --workspace --all-targets -- -D warnings
cargo test --workspace
cargo test --workspace --release
RUSTDOCFLAGS="-D warnings" cargo doc --workspace --no-deps
cargo +1.81.0 check --workspace --lib
```

В текущем `.github/workflows/ci.yml` embedded-проверка явно собирает только `gf2m`, `gfpm` и `rs-codes` для `thumbv7em-none-eabihf`. Новый крейт использует `std` и не должен добавляться в эту проверку без изменения подхода к хранению.

## 6. Ограничения и отложенная интеграция

- `Codelib.md` явно ограничивает матрицы размером `4096 × 4096`, полином — примерно 128 КиБ, сообщение — 4096 байт. Сохраняем эти требования. По действующему README предел полинома считается по памяти коэффициентов одного массива; подробности нужно согласовать с будущим слоем полиномов.
- Предел матрицы относится отдельно к каждой оси. В `gf-linalg` он задаётся `MAX_MATRIX_DIM`; число элементов и размеры рабочих буферов проверяются на переполнение.
- Базовый LDPC-интерфейс работает с одним блоком из `k` битов. 4096 байт исходного сообщения — отдельный предел, его нельзя смешивать с числом столбцов `H`. Правила упаковки байтов, разбиения на блоки, сохранения длины и padding нужно зафиксировать до добавления интерфейса целого сообщения.
- Связь с полиномами ожидает общего типа и его API. Не заменяем её локальным полиномом или заглушкой, которую можно ошибочно принять за выполненное требование.
- Формула `k = n - rank(H)` допускает зависимые проверки. Для кодера нужны `0 < rank(H) < n`; другие матрицы можно использовать для syndrome и декодирования.
- SPA может вернуть допустимое, но неверное кодовое слово, и не гарантирует сходимость на любом графе. Это ограничение описать в README.
- Статус `gf-linalg` в локальном `AGENTS.md` устарел: его README уже описывает обобщённые поля и реализованные операции. Перед следующим этапом сверяться с кодом и CI.
