# coding-core

Общие роли кодеров и декодеров, Rust 1.81, edition 2021. Ядро всегда `no_std`,
без аллокаций, внешних зависимостей и `unsafe`. Оно задаёт команды и смысл
результата; алгоритм и типы данных предоставляет конкретный кодек.

- `Encoder<Input>` кодирует сообщение или готовит сессию блока.
- `Decoder<Input>` возвращает `DecodeOutcome`: кандидат с проверками,
  ожидание дополнительных данных либо остановку без кандидата. Ошибки
  использования возвращаются отдельно через `Result::Err`.
- `SymbolEncoder<Id>` получает часть подготовленного блока по ID.
- `IncrementalDecoder<Input>` накапливает части одного блока; `progress()`
  сообщает состояние, `result()` заимствует доступного кандидата.
- `RepairPlanner`, `RepairHelper`, `RepairExecutor` описывают план ремонта,
  вычисление ответов помощников для конкретной цели и её восстановление.
- `Observer<Event>` принимает события; `NoopObserver` их игнорирует.

Кандидат — предположение декодера. Даже прошедшие проверки не доказывают,
что это отправленный оригинал. `Message`, `Codeword`, `TransformInput`
помогают различать сообщение, переданное слово и вход преобразования.
Проверки и причины остановки имеют собственные типы реализации.

```rust
use coding_core::{MessageBytes, LlrConvention};
let length = MessageBytes::from_bits(17)?;
assert_eq!(length.get(), 3);
let llr = LlrConvention::PositiveForOne.convert(2.0, LlrConvention::PositiveForZero);
assert_eq!(llr, -2.0);
# Ok::<(), coding_core::SizeError>(())
```

Для подключения реализуйте подходящий трейт для своего типа. Входом может
быть структура со срезами, выходным и рабочим буфером. Привязка времени жизни
выхода к такому входу не требует `Vec`. Конструктор кодека проверяет настройки,
порядок позиций и совместимость модели; каждый вызов проверяет форму и контекст.
`MessageBytes` проверяет предел 4096 **передаваемых** байт сообщения;
он не измеряет память Rust-элементов. Трейт сам не может измерить произвольный вход.

Каждый независимый блок обрабатывается отдельно. `NeedMore` означает нехватку
данных и само по себе не обещает их сохранения; накопление между вызовами
предоставляет `IncrementalDecoder`. Реализация описывает обработку повторов,
противоречий и влияние ошибок на состояние и переданные буферы. После признания
накопленных данных непригодными `result()` возвращает `None`.

Минимальный пример подключения кодера, повторяющего один бит трижды:

```rust
use coding_core::{Codeword, Encoder, NoopObserver, Observer};
use core::convert::Infallible;

struct RepeatBit;
impl Encoder<bool> for RepeatBit {
    type Output = Codeword<[bool; 3]>;
    type Error = Infallible;
    type Event = ();

    fn encode(&mut self, bit: bool, _: &mut dyn Observer<()>)
        -> Result<Self::Output, Self::Error>
    {
        // Сообщение всегда один бит, поэтому предел размера соблюдён.
        Ok(Codeword([bit; 3]))
    }
}
let word = RepeatBit.encode(true, &mut NoopObserver).unwrap();
assert_eq!(word.0, [true; 3]);
```

Блочное кодирование, постепенный приём частей и ремонт проверяются в
`tests/contracts.rs`; тестовые кодеки находятся в `tests/support/`.
Кодек с выходным и рабочим буферами вызывающего кода определён в
`tests/support/buffers.rs`. Библиотечный пример `buffers` использует ту же
реализацию для проверки сборки на embedded-цели без `std`.

При мягком входе явно задайте знак LLR, порядок позиций, стирания, поведение
при нуле, NaN, бесконечности и насыщении. `LlrConvention::convert` меняет только
знак. Извлечение сообщения из слова определяется кодеком: это не обязательно
первые `k` позиций.

Из корня workspace:

```sh
cargo test -p coding-core
cargo build -p coding-core --example buffers --target thumbv7em-none-eabihf
```

Тестовые кодеки проверяют использование интерфейсов. Реализации LDPC и RS
пока используют собственные API. Контракты методов и связанных типов описаны
в документации API: `cargo doc -p coding-core --no-deps --open`.
